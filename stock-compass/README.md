# A股右侧交易罗盘 · 本地复刻版

一套本地可跑的**右侧交易决策工作台**：全市场扫描 → 右侧六池 → 个股十二维体检 → 交易计划。
前端单文件、后端纯 Python 标准库，**零第三方依赖**，双击即跑，不需要装任何东西（除了 Python 本身）。

> 数据全部来自公开免费行情接口，所有评分与价位均为算法推算，**仅供研究参考，不构成投资建议**。

---

## 快速开始

### Windows

双击 `start.bat`，或：

```bat
cd stock-compass
python server.py 8092
```

### macOS / Linux

```bash
cd stock-compass
python3 server.py 8092
```

浏览器打开 <http://127.0.0.1:8092>。

### 桌面端（Electron）

不想开浏览器的话，`desktop/` 下是一个 Electron 外壳：无地址栏的原生窗口、托盘、关窗自动停服务。
它**不改任何业务逻辑**，只是把上面那个本地服务装进一个窗口里。

```bat
cd stock-compass\desktop
npm install          :: 首次
启动桌面端.bat        :: 或 npm start
```

打包成单文件便携 exe（约 78MB，产物在 `desktop/dist/`）：

```bat
npm run dist
```

打包出来的 `RightsideCompass-1.0.0-portable.exe` 双击即用，**但仍然需要本机有 Python 3.9+** ——
后端始终是 Python。若想让 U 盘彻底零依赖，把便携版 Python 解压到程序目录的 `runtime\python.exe`，
启动时会优先用它（`main.js` 的 `findPython()`）。

| 位置 | 数据存在哪 |
|---|---|
| 便携 exe | **exe 旁边的 `罗盘数据\`**（缓存跟着 U 盘走，重启不用重扫） |
| 安装版 | `%APPDATA%\rightside-compass-desktop\` |
| 源码运行 | 项目目录下的 `state/`、`data/`（与命令行启动完全一致） |

关窗 = 优雅停服务：先 POST `/api/shutdown` 让 Python 自己收尾（避免正在写 JSON 时被硬杀），
8 秒不退才强杀。服务是你自己在命令行起的（端口已被占用）时，关窗不会动它。

| 参数 | 说明 |
|---|---|
| `python server.py` | 默认端口 8092 |
| `python server.py 9000` | 指定端口 |
| `PORT=9000 python server.py` | 环境变量指定（命令行参数优先） |

**环境要求**：Python 3.9+，无需 pip install。仅监听 `127.0.0.1`，不对外暴露。

启动后服务**会自动触发一次全市场扫描**（`reason: boot`），首次约 2 分钟，之后同一交易日秒开。

## 算法速览

完整推导见 `A股右侧交易罗盘-策略算法与业务逻辑全解.md`（28 章，含每个算法的命中条件原文）。核心三条：

**① 位置分级 —— 只买位置 3**

| | 含义 | 结论 |
|---|---|---|
| pos1 | 追高，在上冲箭头末端买入 | 回避 |
| pos2 | 猜支撑，冲高回落中预测止跌点 | 谨慎 |
| pos3 | 右侧交易，等趋势证明后介入（距 MA20 ≤ 5%） | **推荐** |

**② 右侧成熟度 = 结构 25 + 突破 15 + 量能 20 + 动量 15 + 位置 25 = 100**
综合分 = 成熟度 × 0.6 + 缠论 × 0.4

> 注：全解文档第 26 章术语表里的 `composite_score = 成熟度×0.45 + 缠论×0.35 + 量价×0.20` 是**原站口径**；本地复刻版因量价维度未接通，实际实现为 **0.6 / 0.4 两维合成**（`engine.py:1471`、`engine.py:1631`）。两处不一致属预期，不是笔误。

**③ 四重确认 + 硬性否决**
价格结构 + 量能 + 均线结构 + 市场环境（动量作否决项）。任何 `veto` 命中即"回避"，不看总分。

**右侧六池命中分布**（2026-11-02 实测）：动能 51 / 动量 36 / 趋势 29 / 形态 14 / 回踩 7 / 突破 3。

`/api/report_docx` 是唯一返回非 JSON 的接口：请求体仍是 JSON `{name, content}`，
但成功时回 `application/vnd.openxmlformats-officedocument.wordprocessingml.document`
与 `Content-Disposition: attachment; filename*=UTF-8''...`。前端**先校验 Content-Type**
再触发 `a[download]` —— 服务端出错时回的是 JSON 错误体，直接下载会存下一个装着 JSON 的坏 docx。

任何未列出的 `/api/*` 都会落到 stub，返回 `{"ok": true, "stub": true, "note": "复刻版未接入「XX」的数据引擎..."}`。

检查扫描是否跑完：

```bash
curl http://127.0.0.1:8092/api/health
# running: false 且 phase: "完成" 即结束
```

## 性能与缓存

日 K 是唯一的重活（每只票一个请求）。策略是**磁盘即缓存**：

| 场景 | 耗时 | 外部请求 |
|---|---|---|
| 首次扫描（5000 只 × 日 K） | 80~120 秒 | 约 5000 |
| 同一交易日再扫 | 数秒 | 0（全部命中磁盘） |
| 换交易日后首次 | 同首次 | 约 5000 |

32 并发，实测约 60 请求/秒。每只票的日 K 落盘并记录 `trade_date`，同交易日直接命中，所以是"**首次慢、之后秒开**"。

从 `data/index.json` 的 `td` 字段可以看出当前缓存对应哪个交易日。

## 已修的算法缺陷（2026-11-03）

接缠论 / 量价 / 建仓这几个端点时，在 engine 里查出三处会直接导致**结论方向错误**的问题，已修复：

**① 缠论买卖点与现价脱节（会误否决强势股）**

笔的端点是「最后一个已确认分型」，而最新收盘往往已经延伸出这段笔之外。原实现直接用未完成笔的端点判三类买卖点，于是出现「走势=上涨，却判三卖」的自相矛盾。

实例：贵州茅台 2026-11-02 收盘 1439，在用的向上笔端点只有 1288，而最近中枢 ZG=1338 / ZD=1332 —— 1288 < 1332 满足三卖条件，被十二维体检当成硬性否决，最终 59 分 / `risk` / 回避。
修复后：用收盘价对最后一笔端点做延伸修正，茅台 59 → 79 分，`risk` → `watch`。

同一根因还影响背驰判定的「新高/新低」比较，一并修正。修复后全市场「上涨+三卖」的矛盾样本归零。

**② 筹码分布缺换手衰减（控盘永远判成分散）**

筹码成本分布最初只是把 250 日成交量按价格摊布，不做时间衰减 —— 远月的高位放量会一直压在分布里，把 90% 筹码区间撑到 60%~120%，于是 1252 只里「疑似控盘」命中 0 只，整列全是「分散」。

修复：引入 60 日半衰期的指数衰减，近似逐日换手（公开数据拿不到真实换手率序列）。修复后 ok / mid / no 分布变为 5 / 281 / 966，头部标的（中国建筑 19%、光大银行 16%）能被正确识别为控盘。

**③ 涨停池日期格式（静默返回空池）**

`engine.latest_trade_date()` 给的是 `YYYY-MM-DD`，而东财涨停池接口只吃 `YYYYMMDD`。传错格式不会报错，而是安静地返回空池，页面上就是「涨停 0 家 / 跌停 0 家」。修复后 2026-11-02 实测涨停 125 / 跌停 8 / 最高 6 板。

> 前两条属于**方向性错误**（把好票判成坏票），第三条属于**静默失效**（看起来正常其实是空数据）—— 三种都是最难靠肉眼发现的类型，写在这里提醒后续改动时别退回去。

## 黄金专区（gold.py）的五个坑

黄金是期货，口径和 A 股完全不同，这五条都已在代码里固化，改动前先读：

1. **涨跌幅基准是「昨结算价」，不是昨收盘**（上期所规则）。用昨收算会偏差 0.3% 左右，`goldVsCls` 的高低点染色还会整片染反。
   实测校验：`nf_AU2612` 第 10 字段（839.180）与日 K 上一根的 `s`（结算价）完全一致。
2. **夜盘 21:00-02:30 归次日交易日**；且新浪时间字段可能出现 `9:11:34`（无前导零），
   字符串比大小会把日盘判成夜盘（`"9:11" >= "20:55"` 为 True），必须转分钟数比较。
3. **沪金连续 AU0 是主力拼接序列**，换月有跳空；主力合约必须按各月合约持仓量实时识别（`_resolve_main`），
   写死代码会在换月后静默失真。竞价时点各月合约会短暂返回持仓 0，这时沿用上次识别结果。
4. **内外盘价差要换算单位**：COMEX 是美元/盎司，1 金衡盎司 = 31.1035 克（不是 28.35 常衡盎司），
   再乘 USDCNY。漏掉任一项，溢价会差 6 倍以上。当前实测溢价 ±0.5% 以内。
5. **`%20` 不能用 `%` 格式化拼接**：新浪期货 JSONP 的回调前缀是 `var%20_AU0=`，
   写成 `"var%20_%s=" % sym` 会抛 `unsupported format character '_'`，必须用字符串相加。

另外：期货没有官方「主力资金净流入」口径，成交额 ≠ 净流入，本模块不提供该指标（见 `/api/gold_kb` 的 `not_found`）。

## 研报 / 选股 / 财务的三个坑

1. **残页会覆盖整张快照表（最危险的一个）**：`_snapshot_load()` 原来只要抓到数据就写盘，
   而盘前（09:15 前）绝大多数股票 `price=0` 会被过滤掉，2026-11-04 09:10 实测只抓到 **2 只**，
   直接把 5218 只的快照覆盖成 2 只 —— 之后强势股/右侧六池/情绪全部归零，页面上却看不出错。
   现在改成：**不足 1000 只视为抓取失败，绝不写盘，沿用磁盘旧快照**（`source="disk-stale"`）。
2. **东财 reportapi 的 `beginTime` 是必填参数**，缺了直接 400；带 `cb` 时返回 JSONP，必须自己剥壳；
   `pageSize` 上限 500（传 1000 也只回 500）。
3. **`RPT_LICO_FN_CPD` 同一报告期同一只票有重复行**（2025 年报 count 11534 ≈ 2×5766），
   必须按 `UPDATE_DATE` 去重取最新，否则 ROE 会随机取到旧值。

另外两条口径约定：

- **选股器的过滤在前端**（index.html:13396-13448），`/api/screen` 只做排序 + 翻页 + 计数。
  后端不要重复实现市值/PE/涨幅过滤 —— 两处判断一旦不一致，用户改区间就会踩到"前端筛出来又被后端筛掉"。
- **前端字段名是硬编码的**：`roe_y2025 / roe_y2024 / roe_y2023`。2027 年披露 2026 年报后，
  要同时改前端和 `server.py` 的 `FUND_ROE_YEARS`，否则业绩闸门会一直用旧年份。

## 战法库 / 实时雷达 / Word 导出的六个坑

1. **打分不能直接求和**：18 个判定器高度相关（一个健康的上升趋势会同时触发回踩、金叉、双底），
   加权求和的结果是「命中越多越接近 100」，主榜前 20 名全部顶格，排序等于没排。
   `_tactic_score` 因此改成 **最强一式计 70%、其余各计 12%、封顶 96**：1 式≈66、2 式≈78、
   3 式≈89。阈值也跟着重标（可介入需 `ts≥66` 且右侧命中 ≥2 式）。
2. **战法分饱和之前先看命中率**：`零轴金叉` 最初只要两根红柱一根比一根长就算命中，
   全市场命中率 10.4%，标签等于没有信息量。改成「红柱 ≥1.25 倍放大」后降到 4.3%。
   **加一个判定器之前，先在全快照上量一遍命中率**，超过 8% 的基本都是噪声。
3. **「普涨」不等于「趋势」**：2026-11-05 实测 80.7% 的票上涨，但只有 **24%** 站上上行 MA20。
   只看上涨家数会把反弹日误判成趋势日。`market.width` 因此单独统计
   「站上 MA20 / MA20 上行 / 右侧结构宽度」，环境名会说「反弹普涨 · 右侧结构未修复」。
4. **前端读 `mt.sub.brk`，engine 里叫 `break`**：`tactics.evaluate` 必须自己改名，
   否则「右侧成熟度」列显示「突破undefined」。
5. **实盘页按「战法口径」分表**：`liveRowHtml` 用的是 `r.verdict` 而不是合成结论，
   所以 `liveradar.opportunities` 也必须按 `verdict` 筛行，否则会出现
   「页面显示可介入 5 只、表里只有 4 行」的错账。合成口径只体现在体检列与 ⚠分歧 标记上。
6. **OOXML 子元素顺序是强约束**：`pPr` 里 `spacing → ind → jc → outlineLvl`、
   `rPr` 里 `rFonts → b → color → sz`，顺序错 Word 直接报「无法打开」而不是渲染差异；
   每个 `tc` 必须至少含一个 `p`，每个 zip 部件都要在 `[Content_Types].xml` 登记。
   验证方式不是看 XML 良构，而是 **用 COM 打开数一遍段落与表格**（本机 Word 实测）。

另外：`report_docx` 是全站唯一返回二进制的接口，前端**先校验 Content-Type 再下载** ——
错误时服务端回 JSON，直接 `a[download]` 会存下一个装着 JSON 的坏 docx。

## 数据「不自动更新」的三处锁死（2026-11-05 修）

现象：11-05 盘中打开页面，各页签都写着「数据 2026-11-04」，价格也不动。查下来是**三个独立的锁**，任何一个都会让数据停住：

1. **`latest_trade_date()` 的缓存键错了（最严重）**。原来是 `fetched == today` 就整天复用，
   而新浪日 K **盘中不返回当日那一根** —— 09:06 抓到的必然是昨天，于是把 "fetched=今天"
   写进磁盘，从此一整天都不再抓，**连 15:00 收盘后也切不到今天的 K 线**。
   这不是「慢一天」，是每天第一次抓取就把自己锁在昨天。
   现在改为：只有 `td == today` 才整天锁定，否则按三段重试（盘中 5 分钟 / 收盘后
   15:10~16:30 每 3 分钟 / 其余 30 分钟），当日 K 线一出现立刻切过去。
2. **快照按「交易日」判新鲜**。`_snapshot_load` 原来 `disk.td == td` 就直接读磁盘，
   而 td 一天只变一次 → 盘中快照永不重抓 → 价格定格在最后一次写盘的时刻
   （实测 10:35 写盘后再没动过）。现在磁盘新鲜度按 `ts` 判：盘中 60 秒、盘后 600 秒；
   内存 TTL 也跟着交易时段走（盘中 20 秒、盘后 300 秒），否则「实时雷达」看到的是两分钟前的价。
3. **没有定时器**。原来只在服务启动时 `ensure_scan_async` 一次，进程长开跨天后
   再也不补扫。现在常驻一个 60 秒的 `_auto_update` 线程，幂等地调
   `ensure_scan_async`（它只比较榜单的 `trade_date` 与 `latest_trade_date()`，相等就什么都不做），
   所以盘中不打扰、收盘后 td 一推进就自动起一轮全市场扫描。

顺带修掉的第四个问题：**残页守卫的阈值太松**。原来「不足 1000 只视为抓取失败」，
而盘前抓取时大量 `price=0` 被过滤，2000 条有效行能过线并写盘 —— 实测磁盘上那份只有
2000 行，而盘中完整抓取是 **5572 行**，等于「全市场池」整天只有 2000 只，
页面上完全看不出来。现在加了一条相对判据：**不足上一份的 70% 也算残页**。
修好后强势股从 58 只变 76 只、战法预筛池的「K线不足」从 136 降到 29。

> 一句话记住：**「最近交易日」是「最后一根已收盘日 K」，盘中停在昨天是正确语义**；
> 真正要保证的是「价格随时在动、收盘后能自动切到今天的 K」。

## 后台服务与自动更新

桌面端做成了「窗口 + 服务」两层，和 WorkBuddy 一样的切法：

```
窗口（Electron）   随时可以关，只负责显示；关掉后什么都不影响
CoreService        常驻后台，抓数 / 扫描 / 算榜单，监听 127.0.0.1:8092
```

窗口启动时先探 8092：服务在跑就直接连（秒开、零扫描）；不在跑才自己拉一个临时后端，
关窗时顺手停掉。这样「没装服务的人」和「装了服务的人」用同一份代码，行为都对。

### 注册成 Windows 服务

```bat
install_service.bat      :: 右键 → 以管理员身份运行
uninstall_service.bat    :: 卸载（数据不删）
```

装完就是标准的 `RightsideCompass.CoreService`：

```bat
sc query  RightsideCompass.CoreService
sc stop   RightsideCompass.CoreService
sc start  RightsideCompass.CoreService
```

- 启动类型**自动**，服务意外退出会自动重启（`sc failure`：5 秒后一次，之后每分钟）
- 服务模式的数据在 `%ProgramData%\RightsideCompass`（以 LocalSystem 运行，
  程序目录可能是只读的，写不进去）
- 实现是**纯 ctypes 调 advapi32**，不需要 pywin32 / nssm / srvany，
  和项目「零第三方依赖」的原则一致

不想装服务、又想验证服务模式的行为，用 `python service.py --console` 前台跑一份 ——
它用同一个数据目录、同一条代码路径，只是不注册。

> 注意：部分企业环境 / 安全软件会把 `sc.exe` 列进程序黑名单，此时安装会失败。
> `service.py` 会把提示打成人话（而不是抛 traceback），也可以打开 `services.msc` 手动建：
> 可执行文件填 `python.exe` 完整路径，参数填 `"<程序目录>\service.py" --run`。

### 自动更新

三层结构，和 Electron 生态的通行做法一致：

| 层 | 谁干 | 为什么 |
|---|---|---|
| 版本检测 | 主进程 | 启动后延迟 10 秒比对版本号，不打扰人；菜单「检查更新…」可手动查 |
| 下载校验 | 主进程 | 下到数据目录，用清单里的 `sha256` 校验，不匹配立刻丢弃 |
| 替换文件 | `update_helper.py` | **Windows 不允许替换正在运行的 exe**，必须等主程序退出后由独立进程完成 |

配置放在程序目录的 `update.json`（便携版优先读 exe 旁边那份，改了不用重新打包）：

```json
{
  "enabled": true,
  "feedUrl": "http://你的更新服务器/",
  "checkOnStart": true,
  "checkDelaySec": 10
}
```

`feedUrl` 留空 = **不检查更新**（默认）。宁可没有，也不要每天弹一次「检查失败」。

更新服务器上只要一个 `latest.json`：

```json
{
  "version": "1.0.1",
  "url": "RightsideCompass-1.0.1-portable.exe",
  "sha256": "d6e6a12500b4…",
  "size": 81484741,
  "notes": "修了什么",
  "force": false
}
```

`url` 可以只写文件名（相对 `feedUrl` 解析），换域名不用改清单。
这个文件不用手写，用发布脚本生成：

```bash
python release.py --version 1.0.1 --notes "修复XX"          # 只写清单
python release.py --version 1.0.1 --publish D:\update-server  # 顺便把 exe 拷过去
python -m http.server 8099 --directory D:\update-server      # 临时当更新服务器
```

三种触发方式，对应 WorkBuddy 的自动检测 / 手动 / 命令行：

| 方式 | 场景 |
|---|---|
| 启动时自动检测 | 日常 |
| 菜单 / 托盘「检查更新…」 | 手动 |
| `RightsideCompass-1.0.0-portable.exe --self-update --force` | 脚本、远程运维 |

加 `COMPASS_UPDATE_DRY_RUN=1` 时只下载并校验，**不替换任何文件** —— 排查
「更新为什么失败」时能分清是网络、版本号还是文件本身的问题。

## 桌面端 / 打包的六道坎（2026-11-05）

外壳只有 `main.js` 四百行，但把它做对踩的坑比后端还密：

1. **`ELECTRON_RUN_AS_NODE`**。这个环境变量一旦存在，`electron.exe` 会退化成「纯 Node」：
   不开窗、`require("electron")` 返回 exe 路径的**字符串** → `app.isPackaged` 直接
   `TypeError`，进程闪一下就没了、**一行日志都不留**。`启动桌面端.bat` 里先 `set ELECTRON_RUN_AS_NODE=`，
   并且 `main.js` 的第一行就写日志（含 `packaged/portable/root/store` 四个路径），
   就是为了让这类「双击没反应」有迹可循。
2. **`stopBackend()` 必须幂等**。关窗走 `close`，紧接着 `window-all-closed → will-quit`
   还会兜一次；第二次进来时 Python 往往还没真正退出（`exitCode` 仍是 `null`），
   于是又发一遍 shutdown、又等 8 秒。现在用一个 promise 缓存挡住并发调用。
3. **`/api/shutdown` 写了不等于通了**。当时 `api_shutdown()` 和 `_SRV` 都写好了，
   但 ① 忘了登记进 `POST_ROUTES`，请求落到「未实现该写入接口」的兜底分支；
   ② `_SRV[0] = srv` 从未赋值 → 永远走「服务尚未就绪」。于是桌面端只能硬杀 Python，
   而硬杀可能正好落在 `write_json` 中途，留下半截 JSON。**端到端测一遍才叫实现完**。
4. **便携版的数据会凭空消失**。`electron-builder` 的 portable 包每次启动都把程序解压到
   `%TEMP%` 下的**新目录**，退出即删。数据目录若跟着走，等于每次打开都是空缓存：
   重下 85MB 行情 + 重扫全市场 3 分钟。修法是拿 portable 运行时注入的
   `PORTABLE_EXECUTABLE_DIR` 当锚点，把 `罗盘数据\` 钉在 exe 旁边，
   再用环境变量 `COMPASS_STORE` 通知 Python 侧（`engine.py` / `server.py` / `review.py` / `tactics.py`
   四处路径定义统一读它；不设该变量时行为与命令行启动完全一致）。
5. **`electron-builder` 的网络几乎全靠 GitHub**。这台机器走代理 502、直连超时，
   而构建需要的 `winCodeSign-2.6.0.7z`、`nsis-bundle-3.12.tar.gz` 都在 GitHub Releases 上。
   `ELECTRON_BUILDER_BINARIES_MIRROR` 指到 npmmirror 实测**没生效**（请求仍打 GitHub），
   最后是手动下载 + 校对内置 sha256，放进
   `%LOCALAPPDATA%\electron-builder\Cache\<releaseName>\<文件名>` —— 构建器见到该文件就跳过网络。
   另外 electron 本体也每次重下，改用 `"electronDist": "node_modules/electron/dist"`
   直接复用 npm 装好的版本，200MB 下载彻底消失。
6. **重复构建会被 safe-delete 拦**。产物目录里已有上一轮的 `locales`（58 个文件）时，
   清理动作触发批量删除保护，构建直接失败。把旧 `dist` 改名而不是删除即可。

顺带补掉的一个前端缺口：`index.html` 的 ECharts 加载器是「本地优先 → CDN 兜底」，
但 `vendor/echarts.min.js` 当时并不存在，**断网时所有图表空白**。已把 5.5.0 放进去（1.0MB）。

## 常见问题

**页面是空的 / 一直"加载中"？**
扫描还没跑完。看 `/api/health` 的 `scan.running`，首次需要 2 分钟左右。

**端口被占用？**
换端口：`python server.py 8093`。

**数据是昨天的？**
`data/index.json` 的 `td` 是当前缓存交易日。收盘后新浪日 K 尚未更新时，扫出来的就是上一交易日 —— 这是数据源节奏，不是 bug。等晚上更新后再调 `/api/rescan`。

**能不能部署到服务器？**
默认只绑 `127.0.0.1`。要对外服务需改 `server.py` 里的绑定地址，并自行处理鉴权 —— 当前版本**没有身份验证**（原站的口令门已移除），请勿直接暴露到公网。

**为什么有些模块显示"数据引擎未接入"？**
见上文「尚未接通的部分」。前端保留了原站全部模块入口，后端只实现了能拿到公开数据的那部分。
