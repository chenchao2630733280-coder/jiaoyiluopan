## 第二批端点（累计 10 个真端点）

新增：`mainwave` / `buildupcheck` / `compass_live` / `fib4check`

- **mainwave**：engine 新增 `_mw_breakout()`（回溯最近一次收盘创60日新高）、`_mw_shape()`（麻道明四型：挖坑/蓄势/助跑/井喷）、`_mw_w5()`（张华五维量价线筹盘口）、`mainwave_one()`。A类=突破当日(量比≥1.5+涨幅≥3%+收阳+上影≤40%)；B类=1~10日回踩MA5/MA10±2%且缩量；C类=1~20日回踩MA20±2.5%。候选走全市场成交额前2000（**不用强势榜**，因为突破当天未必满足 MA多头+MACD红柱，会系统漏掉刚启动的票）。实测 A18/B90/C20，4.2s。
- **buildupcheck**：复用 `buildup_one`，零新增算法。注意 `ok` 字段语义是「是否达建仓线」而非请求成功，冒烟脚本会误判为 FAIL，前端用 `r.error` 判错。
- **compass_live**：`{codes}` → 腾讯批量取价，只回 code/price/pct，前端就地改文本。150 只上限。
- **fib4check**：engine 新增 `fib4_one()`。位(回撤位置30%)+态(K线形态20%)+量(量能25%)+动(MACD动量25%)；grade：resonance(四度共振)/triple(三度)/veto(量动同坏)/watch。含陷阱识别与 0.5~0.618 介入带。

踩坑记录：
- `_f`/`tx_raw`/`sym_of_code` 都是 server 内部函数，可直接复用
- mainwave 里 `days==0 and ... or (days)` 的运算符优先级陷阱，已加括号
- 筹码只在买点判定通过后才算（命中率低，先算等于白烧 90% CPU）
- 误删过 api_compass_live 的 docstring，已补回

## position_health（持仓体检）— 严格按原站前端实现

用户给了原站 https://stock-rightside-compass.app.workbuddy.host/#poshealth 说"严格按照这个"。
**关键发现：远端 index.html 与本地 md5 完全一致（896551 bytes / e6fb1ae4…）** → 本地就是原站那份前端，可直接按本地契约实现，不需要猜。

前端契约（index.html:8889-9050 phCard/phRender）：
- 顶层：{items, count, cached, computed_at}
- item：{name, code, price, box{lo,hi,state,level,width_pct,trail_stop,trail_pct,rising_note}, gann{level,weak,note}, time{since_low,budget,stop,moved}, advice, advice_level(ok|warn|"")}
- box.state 必须是「跌破箱体下沿 / 箱体内震荡 / 突破箱体上沿」三选一（前端排序按这三个字符串做 map）
- 前端用 fetch 直连（不经 api()），超时 120s

三个算法（页面文案 4556-4575 明确）：
1. 达瓦斯箱体：摆动低点→高点配对成箱；移动止损 = 近 3 箱下沿最大值，只上移不下移
2. 江恩时间止损：距最近摆动低点交易日数 vs 预算 20 日
3. 50% 回撤法则：最近一条有效上涨腿回撤 >61.8% 视为结构受损

踩到并修的三个坑：
- **gann 全为 null**：原本要求「低点之后存在摆动高点」，但多数票低点后还没形成新分型高点 → 改为取低点之后最高价
- **卖出优先级错误**：平安银行现价 11.54 已跌破移动止损线 11.65，却因回撤仅 32.8% 判成「结构健康持有」→ 新增「跌破移动止损线」判断并提到回撤之前（移动止损是达瓦斯实操核心）
- **箱体序号错**：原来 level 取最近 3 箱的索引，所有票都显示"第 3 箱" → 改为全部箱体计数，实测 21/25/27 箱

接口：无参读 watchlist.json；支持 codes= 覆盖；refresh=1 跳过缓存（内存缓存 30s）。实测 5 只 0.149s。

- **taofei**：七条 = MA30>MA60 / 收盘站上双线 / 涨幅≥5% / 量比≥2 / 上影≤30% / 收盘≥60日高点×0.98 / DIF>0且DIF>DEA。命中≥5 且 score≥55 入选。两型：起涨型(chg20<15)/加速型。score 原始 + score_final 经量价闸门(block -15 / pass +3)。实测 2000 只命中 79。
- **taofeicheck**：`strict=False` 永远回七条明细，便于看哪条没过。

踩坑：
1. 格式化字符串 `"%+.2f%%（≥5%）"` 里中文括号后的 % 未转义 → TypeError，改成 `%%`
2. `vp_counts` 键名错：用 gate 的 pass/block/watch 去比 confirm/warn/mid 的键，统计恒为 0 → 两套键名都输出
3. **漏了 ok_cnt 字段**：前端用 r.ok_cnt 显示「满足 N/7 条」，只给 hits 会永远显示 0/7。`ok` 语义 = 是否构成腾飞点（与 buildupcheck 一致，冒烟脚本会误判 FAIL）
4. 止损距离失控：只用「信号日最低×0.995」在大阳线上给到 -12.9%（青岛食品），MA10 贴近收盘时又给到 -0.44%（阳光照明）→ 改为 MA10 优先 + 上限 -8% + 下限 -2%，实测区间 -1.92%~-8.08%

## ★ 端点名接错（重要教训）

`index.html` 的 `loadDragon()` 调的是 **`api("dragonlist")`**，不是 `api("dragon")`。
我最初把四维榜挂在 `dragon`、`dragonlist` 返回空态 → **页面上龙头页签完全空白**，冒烟测试却是 200/ok，完全看不出问题。
已修：`api_dragonlist()` 直接 `return api_dragon(params)`；席位空态另开 `dragon_seats`。

**教训：拼字段名对不上会报错能发现，但「端点名对不上」只会静默空白。**
以后接任何页签，必须先 grep `api("xxx")` 找到**前端真正调用的那个名字**，不能按页签标题猜。
